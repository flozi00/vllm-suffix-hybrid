## 3b. Capture safety (K5): two-stage split-K, the checklist, the boot gate

**Why.** glm g13/g14 (plugin-harness/dossiers/glm53-speed-2026-10-11.md): an illegal memory access in the
drafter's prefill CUDA-graph capture on all ranks; one of the two suspects is our own small-M dense GEMM
(`sm120/fp8_dense_patch/ours.py` on glm-int): split-K with per-tile counters where the last-arriving CTA
reduces, zero-initialised counter arrays bound to streams on first use. The bisect never finished. This
lane's first design had the same shape (acq_rel ticket per (M, N) tile on persistent counters, one
partial buffer sized lazily and shared by every layer): the leading hazard, so it is gone from the
serving path.

**What serves now.** One Helion body per variant: the Helion kernel writes its fp32 partial per split
(`partial[split, M, N]`), then host code in the SAME body launches the reduce
(`out.copy_(partial[:n_split].sum(0))`: fixed-order fp32 sum, one bf16 rounding) on the same stream.
* The partial comes from `torch.empty` per call (the capture-aware caching allocator: graph-private under
  capture, stream-ordered); `[1, 1, 1]` stub when the config does not split (never read).
* No counter, no atomic, no barrier, no module-level scratch (`tests/test_helion_mxfp8_gemm.py`
  `test_triton_codegen_semaphore_free_by_default` asserts it on the Triton source Helion generates for
  both bodies, static and dynamic shapes; `test_no_module_level_scratch_or_counters` guards the rest).
* The lab (`KERNELS`, `lab_main`) tunes and times the whole composite, reduce included, so
  `split_k` is only picked where it pays for the two extra launches (single launch when it does not).
  The roofline model in section 2 shows the price: a tuned split costs +2 launches (~4 us) per call;
  the old design hid that cost in a semaphore. Follow-up if the lab shows split-K wins: a one-launch
  reduce (a Helion kernel behind a custom op) or folding the reduce into the consumer.
* K5: `prepare()` / `register()` raise when `SUFFIX_MXFP8_GEMM_SEMAPHORE=1` ("UNPROVEN under CUDA-graph
  capture ... the serving lane never serves it"); the layer oracle runs NaN-poisoned, then captures the
  call in a CUDA graph on a side stream, replays it with new data and requires bit-identity with eager,
  one M per bucket, fatal on mismatch (`mxfp8_gemm.capture_check`).
* The semaphore variant (`mxfp8_gemm_sem` / `mxfp8_gemm_a8_sem`: same device loop and ConfigSpec, so
  configs transfer) stays for lab A/B and for bisecting the g14 fault: `lab_main` and
  `--variant semaphore` of the gate accept it only with `SUFFIX_MXFP8_GEMM_SEMAPHORE=1`.

**Capture-safety checklist** (any lane that runs inside a vLLM CUDA graph; the right column is this lane):

| # | rule | this lane / how it is checked |
|---|---|---|
| 1 | No raw allocation inside capture: no `cudaMalloc/Free`, no pinned / managed alloc, no tensor built from host data (`torch.tensor(list, device=cuda)`, `.to(cuda)` from pageable memory) | only `torch.empty` (`out`, `partial`); the oracle and gate run with the caching allocator ON |
| 2 | No stream or event creation inside capture; side streams exist before capture and are joined with events recorded in the graph | the lane never creates a stream and runs on the capturing stream; the gate captures on a side stream |
| 3 | No host sync or host-visible dependence inside capture: `.item()`, `.cpu()`, `.tolist()`, `bool(t)` / `int(t)`, `torch.cuda.synchronize()`, data-dependent shapes (`nonzero`, `masked_select`), Python control flow on tensor values | `gemm` / `apply` / `_op_impl` branch on Python ints only; the weight check and oracle syncs run at load |
| 4 | Scratch: only (a) torch's allocator inside the op, or (b) load-time persistent buffers with a stable pointer that never grow, shrink or get replaced after the first capture. Nothing lazily sized and shared between layers or streams, nothing bound at first use, nothing that must be zero at launch (counters, semaphores, flags) | no module-level state at all (`_SCRATCH` / `_NEED` deleted; regression test) |
| 5 | No cross-CTA ordering assumption (semaphores, last-block-done reduce, atomic barriers, spin waits) unless forward progress and co-residency are proven and sanitizer-checked; stream order is the synchronisation | stage 2 is a second launch; Triton source of the served bodies has no atomic / `debug_barrier` |
| 6 | Every specialisation compiled and loaded BEFORE capture: Triton compile, `cuModuleLoad`, `cuFuncSetAttribute(max dynamic smem)`, Helion bind. Contract of `hk.compiled()` + `warm_ms()`: M = 1, each bucket top and top - 1 (the `M % 16` class), every distinct split value (the partial's first dim is specialised) | the layer oracle warms the plan at load; gate probes run eager before capture |
| 7 | Replay-invariance: a replay must not read what the previous replay left behind except through tensors the graph declares | NaN-poisoned `out` / `partial` inside the captured region (`poison_nan`), exact check on the eager result, bit-exact compare on every replay |
| 8 | Pointers baked into the graph stay valid: inputs are static tensors updated in place, outputs are read before the next replay, graph-private pools are never shared by graphs that can replay concurrently | gate: changing inputs, cycled order, guarded output, two graphs replayed on two streams |
| 9 | A fault must name its kernel: print the label before running it, keep `CUDA_LAUNCH_BLOCKING=1` and a single-probe filter at hand | gate prints `PROBE <label>` first; `--only`, `--no-capture` |

## 5. Lab run (one PRO 6000 Server Edition, one command)

## 6. Drift / quality gate plans (AGENTS.md section 5; none of these is assumed to pass)

Common: A1 -> roll B -> B -> roll back -> A2 on one idle dev pool with the same 8 GPUs; `bench-chain`

* **6A mxfp8_gemm A8 / wo_a A16 (same numerics as stock up to accumulation order)**: reordering class.

  NOT the same function as stock (it is closer to the BF16 reference). Treat as approximation class:

* **6D Markov W2 -> MXFP8 (if the bench says it is worth it)**: draft-side; target verification keeps the

## 8. Risks

* Helion's front end lowers every body and every probe config to Triton source (CPU-tested), but
  Triton / ptxas has not compiled any of it for sm_120 yet. `dot_scaled` with e4m3/e4m3 and u8 scales
  on sm_120a, and `view(torch.float16)` bit tricks in a Triton prologue, are the likeliest compile
  failures; both fail loudly in the lab (the gate reports them as NOT RUN), not in serving.
* The lane replaces vLLM globals (`modelopt.select_linear_kernel`, `init_mxfp8_linear_kernel`,
  `deep_gemm_fp8_o_proj` in `deepseek_v41.nvidia.ops.o_proj`); `register()` raises when an anchor is
  gone. A vLLM bump needs a re-read of these three seams (verified against 39983a5e7 here).
* Switching the fused q/kv-RMSNorm MXFP8 producer off (our kernel has `input_quant_key() -> None`):
  prefill (M > max M) falls back to unfused act quant for wq_b / indexer.wq_b - one extra small
  kernel per layer in prefill only.
* Scratch is per call from torch's allocator, so layers and streams never share it (the old shared
  buffer assumed everything ran on the default stream). The residual capture risks are the ones a CPU
  cannot see: a Triton specialisation compiled during capture (checklist 6; a first call inside capture
  raises, it does not silently compile) and the allocator reusing a block inside a graph pool
  (poisoned in the oracle and gate).
* Two extra launches per split call (torch sum + bf16 copy) may erase the split-K gain on the smallest
  shapes; the tuner sees that cost, so the likely outcome is split_k = 1 almost everywhere and the win
  coming from wo_a bytes and the removed activation-quant launch. Honest until the lab says otherwise.
* `wo_a` A16 at M = 192 is BF16-MMA bound in the model (no byte win, equal time); keep bucket 192 on
  vLLM unless the lab shows otherwise.
