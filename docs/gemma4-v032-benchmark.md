# Gemma 4 26B A4B: vLLM 0.32 / Helion experiment

Development only. Production `gemma4-26b-a4b-v3` remains on vLLM 0.30.0 and plugin `88925ecc`. The target is at least 10% higher geometric-mean output throughput over six scenarios at concurrency 1, 8 and 32, with no speed loss, new request errors or quality regression. The target has **not yet been demonstrated**.

The candidate starts from merged Helion PR #18 (`db8dac5f`). It adds a source-pinned vLLM 0.32 adapter, preserves the swizzled C++ NVFP4 cache format, and guards real image prefills from FULL decode graphs. Missing or slower Helion shapes retain oxide. There is no serving-time tuning.

- Both arms retain the existing NVFP4 weights and dense conversion, MTP width 3, 128,000 context, 32 sequences, page size 64, image support and tool/reasoning parsers.
- A common image-padding correction handles 31 real request flags with 32 graph-padded query offsets. The original baseline image crash is retained in the artifacts.
- Five baseline speed rounds are complete. One thinking/concurrency-8 block returned 31 HTTP 500s; its cause is unknown. All five follow-up rounds were clean. The failed block must not inflate any reported improvement.
- Full quick quality runs (3,244 items each) on the baseline 5090 and candidate healthy MaxQ returned zero request errors. The hardware-crossing comparison is diagnostic and cannot establish an upgrade speed or numerical pass.
- Unchanged baseline prompt scores were unstable on the same pod/card, with and without MTP. A plausibility self-check is insufficient. The optional ordered reduction subsequently made three candidate repeat runs identical; both reference and candidate are now exactly repeatable in three unchanged-pod runs. The cross-version distribution still fails the strict drift gate. Thresholds are unchanged.

`SUFFIX_NVFP4_MOE_ORDERED_FINALIZE=1` is an optional investigation of upstream [vLLM #54945](https://github.com/vllm-project/vllm/issues/54945). It requests FlashInfer's ordered expert reduction only for NVFP4 fallback calls; native/Helion decode dispatch is independent. It defaults off. Three v0.32 Gemma repeat runs were identical (KL 0, top-1 100%, perplexity ratio 1); the v0.30 reference also repeated exactly. On the same physical GPU, the two-document diagnostic still gives KL 0.071–0.218 and top-1 agreement 85.9–95.3%, exceeding the unchanged KL <=0.005 / top-1 >=98% gate. The same correction is prepared for both numerical-reference arms. The original speed data is retained. A fresh ordered A1/B/A2 sequence on GPU1 provides the controlled reference after the hardware migration.

The first 5090 K2 search reported a provisional 1.2816x kernel result for D256/H16/KV8, width4, batch1 (14.472 versus 18.547 microseconds). D512/width4/batch1 lost (0.9924x) and retains oxide. A dynamic-shape width4/batch32 D512 search measured only 1.0272x, but its cache protocol is also unqualified; it is retained as a search result only. Corrected cold-cache measurements predeclare a 1% minimum per-shape gain in both timing orders, followed by end-to-end validation. The initial config is quarantined: the lab summed overlapping row views and counted inactive SWA storage, so its timing did not establish cold-cache performance. The corrected accounting counts active physical pages once, caps actual allocation, and records the achieved rotation footprint. Kernel results are not end-to-end gains. Search now explicitly matches serving's dynamic shapes and caps total LFBO time, including polishing, at 900 seconds.

The 5090 MoE sweep tested 60 schedules and found all bit-identical to the existing native plan. The existing serving settings are close to the measured optimum. The candidate v0.32 model and drafter loaded on one 5090 using 17.66 GiB for weights; it served with 5.87 GiB of KV cache (462,802 tokens, engine estimate 3.62x128k). The first 40-item 5090 smoke test had zero errors. No 10% serving gain has been established.

Raw specs, immutable overlay IDs, logs, thermal telemetry, failed attempts and benchmark runs are in the sibling console repository under `benchmarks/runs/gemma4-helion-20261018/`. `gemma-v032-experiment.json` describes the contract. No production promotion is authorized by this experiment.

During the ordered candidate rollout, the lab finished and the dev pod moved from worker-03 GPU2 to GPU1. Another deployment took GPU2. The affected screen is retained as a different-card diagnostic. A fresh A1/B/A2 reference sequence on GPU1 now checks the actual UUID after readiness; checking only total GPU allocations before a roll was insufficient. Production Gemma image, plugin, settings and pod identity remain unchanged.

K2 configuration keys now retain every exact query width 1 through 8, including dynamic-speculation widths 2 and 6. A width-4 configuration cannot qualify either shape. A bounded fixed-config preflight measures active storage across at least three L2 caches where the allocation budget permits; insufficient rotation or any oracle failure cannot qualify a configuration. No 5090 K2 configuration is currently shipped.
